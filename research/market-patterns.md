# GitHub 优惠监控项目研究

研究日期：2026-11-04。这里只记录可复用的工程模式，不把社区爆料当作已核验价格，也不复制第三方项目的私有凭据、反爬绕过或购买自动化。

## 时效性与准确性深挖

### 可量化时效

- `CallMeByYourName/smzdm-monitor` 的历史样本覆盖 700 次运行，其中 696 次成功、4 次因 GitHub runner 未分配而失败；连续样本的平均运行时间约 233 秒、扫描时间约 217 秒。它用运行日志持续观察失败率、扫描耗时、候选量和推送量。
- `zhdash/hxm5-monitor` 记录到 GitHub 定时任务实际间隔可能远差于标称频率，因此改为单次触发后在任务内长循环。本项目使用 Windows Task Scheduler，仍应记录“来源发布时间 → 本地发现 → Bark 成功”三段延迟，而不能只看计划任务的 `LastTaskResult=0`。
- 线报 RSS 的 `max-age=300` 决定发现延迟下限。单纯增加轮询频率不会突破源站缓存；要继续提速，只能使用源站允许的事件/推送接口或更快的独立来源。

### 可验证准确

- 历史复盘发现，即使规则复杂的 SMZDM 监控，也曾有约 13% 的推送不是可购买商品，例如直播间、抽奖、任务、返利页和券合集。这说明“能解析到价格”不等于“可执行好价”。
- 最有效的准确度组合是：明确总价/单位价、购买门槛、数量、规格、渠道、有效期、可复现步骤和商品入口同时存在；缺少购买条件时降级或拒绝。
- 社区互动、热榜、评论数只能表示关注度。价格优势需要历史同口径价格或可见结算证据；不同数量、会员、返利和规格不能直接比较。
- 同一内容换帖子 ID、不同作者重复转发会造成重复推送。需要 ID 去重之外的内容指纹，但指纹过短或包含动态时间时应禁用，避免误合并。
- 推送失败不能提前写成已处理。应保存 pending 队列并优先补发；只有成功或明确耗尽重试后才从队列移除。

### AI 价格核验

- AI 适合做同款识别、规格/数量对齐和公开历史价格检索，但不能把模型记忆、划线价或“历史低价”宣传语当作证据。
- 只有同款、同规格、同数量、同渠道的近期价格记录才能参与降幅计算；默认要求当前到手价比可核验历史价低至少 30%。
- AI 必须返回公开证据 URL、置信度、历史价和降幅；超时、认证失败、同款不确定、历史证据不足时一律拒绝推送。
- 当前仓库已提供 Codex CLI 适配器和 JSON Schema，但本机 Codex CLI 认证不可用，因此默认关闭 AI，先由确定性历史价门槛保证低噪声。

### 本项目新增指标

- 记录 `sourceToDetectionSeconds`：来源发布时间到本地发现的延迟。
- 记录 `sourceToNotifySeconds` 和 `detectionToNotifySeconds`：来源/发现到 Bark 成功的延迟。
- 增加跨帖子 `contentFingerprint`，相同规范化内容在 7 天内只推送一次。
- 投递成功状态继续幂等；未成功的候选仍可由后续轮次重新评估。

## 市场主流做法

### 获取速度

1. **先抓列表，再富化详情**。列表请求用于发现和排序，只对高优先级候选请求详情，避免把请求预算浪费在普通促销上。
2. **增量扫描优先**。按时间倒序处理，发现连续旧数据后停止翻页；定期强制完整扫描，防止游标漂移漏项。
3. **持久化未处理队列**。超过单轮详情或推送预算的候选留在状态中，下一轮继续处理，而不是静默丢弃。
4. **速度受源站缓存约束**。本次实测 `new.xianbao.fun/rss.php` 返回 `Cache-Control: public, max-age=300`。因此 5 分钟是当前 RSS 的合理生产轮询间隔；30 秒轮询只会读取缓存并增加限流风险。
5. **分级时效**。错价、零元和库存漏洞使用 30 分钟窗口；叠券和渠道专属使用 6 小时窗口；任何超过 24 小时的购物线索不推送。

### 推送及时性

1. **事件驱动推送**。一旦候选通过质量和去重检查，就在同一轮立即投递，不等待用户询问。
2. **冷启动抑制**。第一次运行只建立基线，避免把已有历史一次性推爆。
3. **幂等去重**。使用 `source + sourceId` 标识商品，用价格、券态、数量、规格、渠道和操作步骤的指纹识别实质变化。
4. **投递分级**。新鮮的错价、零元和库存异常使用 Bark `timeSensitive`；其他合格线索使用 `active`，避免所有消息都抢占最高优先级。
5. **失败可重试、成功才记账**。Bark 请求做有界重试；只有确认返回成功后才调用 `MarkSent`。

### 准确度

1. **多信号准入**。价格、动作步骤、券领取、叠加顺序、结算证据、商品链接、时效共同评分；单纯“便宜”或“历史低价”不算信息差。
2. **硬证据门槛**。叠券必须同时有领券和叠加/加车/凑单证据，并有至少两步可复现动作；拍发异常必须有错发或收到规格不一致证据。
3. **价格语义分离**。区分总到手价和单位价，例如 `共16斤21亓` 是总价，`1.3亓/斤` 是单位价，不能把后者显示成总到手价。
4. **来源声明透明**。线报酷内容标记为“未核验”，保留来源链接和观测时间，不把社区爆料写成平台确认价。
5. **风险标记**。88VIP、PLUS、限购、返利、抽奖和凑单会降低置信度并进入状态审计，但不能被误写成已核验优惠。

## 本次落地

- 把候选按异常类型和来源时间排序，优先使用详情请求预算。
- 将详情预算从 8 提高到 16，将单轮提醒上限从 2 提高到 4；质量门槛会压掉普通促销。
- 将线报回看窗口从 12 小时收紧到 3 小时，减少陈旧线索参与详情抓取。
- 新增 `scripts/deal-quality.ps1`，实现价格语义解析、独立证据硬门槛、0–100 质量分、风险标记和推送优先级。
- 修复 `10元` 中 `0元` 子串、`拍5发150粒` 被误判为错发，以及 `亓`/单位价无法解析的问题。
- Bark 支持 `active`、`timeSensitive` 等级别和点击来源链接；消息正文继续不带图片。
- 状态记录增加价格口径、质量分、置信度和推送级别，方便复盘误报与漏报。

## 暂不采用

- 不登录、不下单、不领券，不绕过验证码、风控或反爬。
- 不抓取 `robots.txt` 禁止的 `/search`、`/link`、`/smzdm/` 和 `/category-smzdm/`。
- 不默认调用 LLM；当前规则必须可解释、可测试且离线可运行。
- 不用评论数、值率或热榜位置证明价格优势；这些只能表示社区关注度。
- 不把 RSSHub 公共实例用于长期高频生产监控；SMZDM 生产订阅应使用自托管 RSSHub。

## 后续路线

1. 为商品建立价格历史和单位价格归一化，支持目标价与历史最低价对照。
2. 增加多个独立来源交叉验证，只有来源间价格、券态或步骤一致时才提高置信度。
3. 保存 Bark 投递结果和用户反馈，定期复盘误报、漏报、消息时效和命中率。
4. 对高价值候选做延迟复查，确认活动仍有效后再发送“补充/失效”更新。

## 自动化可移植性

`SKILL.md` 本身不会执行定时任务。仓库内的 `scripts/install-monitor-task.ps1` 可在 Windows 注册无窗口计划任务；其他环境仍需使用 cron、systemd timer、GitHub Actions 或平台自动化调度。任何人部署前都必须配置自己的 Bark 密钥，并先用 `-DryRun` 验证。
